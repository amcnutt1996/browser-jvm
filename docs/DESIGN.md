# Java Runner design

> Written while the runner lived in gregOS; paths are gregOS paths. See
> [docs/README.md](README.md) for where they are in this repository.

This records every architecture decision for the gregOS Java runner, with the
reasoning and data behind it. Decisions were made during an unattended run; each
one says what would make it worth revisiting.

Data comes from `docs/java-runner/RECON.md` (generated by
`scripts/javaRunner/recon.ts`) unless noted.

## 1. Execution model

**Decision: an interpreter over an explicit frame stack, with green threads
scheduled by the JVM, running inside a dedicated Web Worker.**

- Every Java method invocation pushes a `Frame` object (`method`, `pc`, `locals`,
  operand `stack`, `sp`) onto the owning thread's frame stack. The interpreter
  loop never recurses into JavaScript for a Java call, so any thread can be
  suspended between any two instructions and resumed later from a timer,
  animation frame or I/O callback.
- Threads are green threads. The scheduler runs one thread at a time for a
  slice (instruction budget checked at backward branches and invocations), then
  switches. `synchronized`, `wait`/`notify`, `sleep`, `join`, `park`/`unpark`
  and interrupts are implemented on top of that: a blocked thread is simply not
  runnable until its wake condition happens.
- Natives are JavaScript functions. A native that must block (sleep, wait for
  the next animation frame, read a file from the gregOS file system) returns a
  promise-like suspension and the thread resumes with the result. A native
  that needs to call back into Java (for example `toString()` on an argument)
  is written as a generator that yields invocation requests, so it never needs
  a nested interpreter loop and stays suspendable.
- `<clinit>` runs as a normal pushed frame: the triggering instruction is
  re-executed after the initializer returns, which gives exact JLS
  initialization order including recursive and failed initialization.

**Worker vs main thread.** The JVM runs in a Web Worker in the browser:

- The interpreter is CPU-bound. On the main thread it could only take part of
  each frame budget and every slice would compete with gregOS's own React
  rendering and window dragging. In a worker it gets a whole core and the
  desktop stays responsive by construction ("don't freeze the desktop").
- gregOS already renders from workers with `OffscreenCanvas`
  (`components/system/Taskbar/Clock/clock.worker.ts`, the wallpapers), so this
  matches existing conventions. WebGL2 works on an `OffscreenCanvas` in a
  dedicated worker, and `requestAnimationFrame` exists there.
- Isolation: nothing the JVM does (timers, typed array views, global state)
  can interfere with gregOS's own main thread.
- Closing the window terminates the worker, which is the cleanest possible
  shutdown: no Java code can keep running and all memory goes away.
- Costs: input events, audio and file system access cross `postMessage`.
  Input is forwarded as small messages; audio is decoded and played on the
  main thread (`AudioContext` is not available in workers); file reads and
  writes are asynchronous requests, which green threads absorb naturally (the
  calling Java thread suspends until the reply arrives).

The engine itself (`components/apps/JavaRunner/jvm/`) has no DOM or worker
dependency. A small `Host` interface supplies output streams, files, time and
graphics, so jest runs the same engine headless in Node.

Revisit if: workers turn out to lack something essential (they don't for
Chromium, Firefox 105+, Safari 16.4+).

## 2. Value representation

| Java | JavaScript |
| --- | --- |
| `int`, `short`, `byte`, `char`, `boolean` | `number`, always normalized (`\|0`, `<<24>>24`, `&0xffff`, …) |
| `float` | `number` rounded with `Math.fround` after every operation |
| `double` | `number` |
| `long` | `bigint`, normalized with `BigInt.asIntN(64, …)` |
| reference | JS object, or `null` |
| `java.lang.String` | JS primitive string |
| `int[]`, `byte[]`, … | `Int32Array`, `Int8Array`, `Uint16Array` (char), `Int16Array`, `Float32Array`, `Float64Array`, `BigInt64Array`, `Int8Array` (boolean) |
| `Object[]` and other reference arrays | JS `Array` |

Every array carries a `$cls` property for its array class. Objects are
instances of a per-class JS constructor whose prototype holds `$cls`, so
fields become hidden-class properties and dispatch reads `obj.$cls`.

Exact semantics handled explicitly: `idiv`/`irem`/`ldiv`/`lrem` by zero throw
`ArithmeticException`; `Integer.MIN_VALUE / -1` wraps; `f2i`/`d2i`/`f2l`/`d2l`
saturate and map NaN to 0; `fcmpl`/`fcmpg` differ only on NaN; shifts mask
their count (`& 31`, `& 63`); `char` is unsigned 16-bit; `frem`/`drem` use JS
`%` (same as C `fmod`, which is what Java specifies).

**long as BigInt — benchmark.** A `java.util.Random`-style LCG step (multiply,
add, mask, shift) run 5,000,000 times in Node 22: BigInt 135 ms, hand-written
pair of int32s 51 ms; a plain BigInt add+wrap is ~7 ns vs ~1 ns for an int add.
The pair representation is 2.6× faster but makes every long operation, every
long field, array and call site twice as complex. The game is int/float heavy
(recon: `Math` and `Integer` in hundreds of classes, longs mostly for time and
`Random`), so per frame long arithmetic is in the thousands of operations at
most, well under a millisecond with BigInt. BigInt it is; the JIT (milestone 8)
can revisit hot long code if profiling ever points there.

**Strings are JS strings.** `java.lang.String` values are primitive JS strings.
String methods are natives over JS string operations, string concatenation is
`+`, and passing text to the browser (shader source, file names, console
output) costs nothing. Dispatch on a receiver uses `vm.classOf(value)`, which
checks `typeof value === "string"` before reading `$cls`, so no built-in
prototype is modified. The one semantic difference: two distinct `String` objects with equal contents compare
equal with `==`. Code that relies on `new String(s) != s` is rare and fragile anyway; `IdentityHashMap`/`System.identityHashCode`
on strings fall back to content. `new String(...)` allocates a placeholder that
the constructor replaces in the caller's frame.

**Identity hash codes** are assigned lazily from a xorshift sequence and
stored on the object (`$hash`). **Monitors** are allocated lazily (`$mon`).

## 3. Class library

**Decision: a hybrid. A small core written for this runner (Java source plus
JavaScript natives), with everything else taken unmodified from OpenJDK 21's
`java.base` and selected by a closure script.**

Data from recon:

- The game-reachable set (3,564 classes reachable from `DesktopLauncher` when
  the LWJGL3 backend is replaced) references 177 JDK classes; the whole jar
  252. The heavy hitters are exactly the classes any JDK class library has to
  get right: `Object`, `String`, `Class`, `Math`, `Integer`, `StringBuilder`,
  `ArrayList` (535 classes), `Iterator`, `HashSet`, `LinkedHashMap`,
  `HashMap`, `Arrays`, `Collections`, `LinkedList`, `regex`.
- `invokedynamic` uses exactly two bootstraps:
  `StringConcatFactory.makeConcatWithConstants` (414 sites, all in the Java 11
  game classes) and `LambdaMetafactory.metafactory` (185 sites, all in Java 8
  libGDX/LWJGL classes). No `altMetafactory`, no records, no switch
  bootstraps. Both are handled directly by the interpreter, so none of
  `java.lang.invoke` is needed beyond small `MethodHandle`/`MethodType`
  shims for reflection-style use.
- No `ServiceLoader`. Reflection is limited to libGDX's `ClassReflection`
  wrappers (used by its `Json` and pools), `org.json`, and SPD's
  `Class.isInstance`/`isAssignableFrom`/`getSimpleName`/`getEnumConstants`.
- Files go through `java.io.File`, `FileInputStream`, `FileOutputStream` and
  `RandomAccessFile` (libGDX `FileHandle`); `java.nio.file` only in LWJGL and
  Jamepad, which are replaced. Saves use `GZIPInputStream`/`GZIPOutputStream`
  (`Deflater`, `CRC32`).
- `java.text` (`SimpleDateFormat`, `DecimalFormat`, `MessageFormat`),
  `Calendar`/`TimeZone` and `Locale` are used by the game (rankings dates,
  number formatting, `Messages.format`).

Option (b), booting real `java.base` through `System.initPhase1..3`, would
drag in modules, the `java.lang.invoke` infrastructure, `jdk.internal.misc`
VM bootstrapping, `ScopedMemoryAccess`-based NIO and compact-string internals,
for no benefit here: the game needs none of it. Option (a), hand-writing all
of `java.util`, `regex` and `Formatter`, is a large amount of duplicated,
error-prone work when OpenJDK's pure-Java implementations are available and
redistributable (GPLv2 with Classpath Exception).

So, concretely:

- **Own core** (in `components/apps/JavaRunner/java/`, compiled with `javac`
  by `scripts/javaRunner/buildRuntime.sh`): `Object`, `String`,
  `AbstractStringBuilder`/`StringBuilder`/`StringBuffer`, `Class`, `System`,
  `Runtime`, `Thread`, `Throwable` (stack trace natives), `ClassLoader`,
  boxing/`Math`/`StrictMath`/`Float`/`Double` natives, `java.lang.reflect`,
  `java.lang.ref`, the `java.nio` buffers (backed by typed arrays so they can
  go straight to WebGL), `java.io` file classes over the gregOS file system,
  `java.util.zip` over `fflate`, and `jdk.internal.misc.Unsafe` for the
  borrowed classes that need it (`ConcurrentHashMap`, atomics, locks).
  Own versions exist only where the OpenJDK class depends on VM internals,
  compact-string internals or a heavy subsystem.
- **Borrowed**: everything else the closure script finds reachable,
  byte-for-byte from the local JDK's `java.base.jmod`.
- Both are packed into one runtime jar shipped with the app. The own classes
  win over borrowed ones on name clashes.

Revisit per class: when a borrowed class's static initializer pulls in a
subsystem (locale providers are the expected one), replace that class or the
subsystem entry point rather than emulating the subsystem.

## 4. Browser bridge

**Decision: the high-level seam.** The runner supplies its own
`com.badlogic.gdx.backends.lwjgl3` classes (`Lwjgl3Application`,
`Lwjgl3ApplicationConfiguration`, `Lwjgl3Graphics`, `Lwjgl3Input`,
`Lwjgl3Files`, `Lwjgl3FileHandle`, `Lwjgl3Preferences`, `Lwjgl3Window`,
`Lwjgl3WindowListener`, `Lwjgl3Clipboard`, the GL20/GL30 implementation and an
audio implementation) that talk to WebGL2, forwarded DOM input and Web Audio.

Data: below that seam sit 4,479 LWJGL natives (2,237 in `org.lwjgl.opengl`,
2,027 in `org.lwjgl.system`, 215 in `org.lwjgl.stb`) plus LWJGL's own
`sun.misc.Unsafe` use in 118 classes, all of it raw-pointer code. None of it
is reachable once the backend is replaced (recon: 0 reachable LWJGL natives
from the game set). The game's own desktop classes touch the backend only
through `Lwjgl3ApplicationConfiguration`, `Lwjgl3Preferences`,
`Lwjgl3FileHandle`, `Lwjgl3WindowListener`, `Lwjgl3Application`,
`Lwjgl3Graphics(.Lwjgl3Monitor)`, `Lwjgl3Window` and, in the crash handler,
LWJGL's `TinyFileDialogs`.

Natives that still get through (all in libGDX, implemented in JavaScript):

- `Gdx2DPixmap` (17): image decode, blits and primitive drawing on RGBA buffers.
- `FreeType` (60): the game renders text with gdx-freetype from
  `fonts/pixel_font.ttf` and `fonts/droid_sans.ttf`.
- `BufferUtils` (30): copies and transforms between arrays and buffers.
- `Matrix4` (3: `mulVec`, `prj`, `rot`).
- `ETC1` (8): not used by the game; left unimplemented.
- `org.lwjgl.util.tinyfd` (11): only reachable from the crash dialog; the
  runner's crash handler prints instead.

Images: PNG decoding is done by a small synchronous decoder on `fflate`, so
`Gdx2DPixmap.load` stays synchronous and works in Node tests. Audio: Ogg and
MP3 bytes are handed to the browser's `decodeAudioData` instead of running
jorbis/javazoom in bytecode.

## 5. Code layout

- `components/apps/JavaRunner/jvm/`: the engine. No React, no DOM. Class file
  parser, zip reader, class loader, interpreter, threads, natives.
- `components/apps/JavaRunner/java/`: Java sources for the runner's own
  classes (core library and libGDX backend). Compiled by
  `scripts/javaRunner/buildRuntime.sh` together with the borrowed OpenJDK
  classes into `public/System/JavaRunner/runtime.jar`, which is committed so
  neither tests nor the app need a JDK.
- `components/apps/JavaRunner/`: the gregOS app (`index.tsx`, `useJavaRunner.ts`,
  the worker entry).
- `__tests__/components/apps/JavaRunner/`: jest tests; conformance programs
  and their expected output live next to them.
- `scripts/javaRunner/`: developer tools (recon, runtime build, conformance
  test generation). Run TypeScript tools with
  `node --import ./scripts/javaRunner/register.mjs <script.ts>`.

## 6. Decisions made while building milestones 1 and 2

- **Lint configuration.** `oxlint.config.mts` has an override for
  `components/apps/JavaRunner/jvm/**` that turns off rules a JVM cannot follow:
  `no-bitwise` and `no-labels` (bit operations and the dispatch loop are the
  instruction set), `unicorn/no-null` (Java `null` is JS `null`),
  `no-param-reassign` (natives fill in the Java objects they receive),
  `typescript/only-throw-error` (`JavaThrow` is deliberately not an `Error`, so
  a Java exception does not pay for a JS stack capture), `operator-assignment`
  (operand stack slots are `unknown`), `no-continue`, and the code point /
  encoding name rules (Java's charset names are upper case).
- **Interpreter control flow.** A frame that calls out records `resumePc`; a
  callee's return value is pushed only when the caller has one, so the same
  path serves invocations, re-executed instructions (class initialization) and
  deferred monitor acquisition (`pendingLock`). Generator natives are frames
  too; they receive callee results and wake-up values through `genValue` and
  `JThread.resumeValue/resumeError`.
- **Stack overflow.** Java frames are JS objects, so deep recursion cannot blow
  the JS stack; a hard limit of 6,000 frames per thread raises
  `StackOverflowError` instead of exhausting memory.
- **Exceptions created by the VM** (`NullPointerException`, `ClassCastException`
  and so on) are built without running Java constructors. Every class in
  `VM_EXCEPTIONS` is initialized during boot so this never needs a `<clinit>`.
  Messages follow HotSpot's wording, including module descriptions in
  `ClassCastException` (the runtime library counts as `java.base`, everything
  else as the unnamed module of loader `app`).
- **Own classes added beyond the plan, and why:**
  - `java.lang.JavaLangAccessImpl`: borrowed classes reach `String`, `Class`
    and `Thread` internals through `SharedSecrets.getJavaLangAccess()`. The
    implementation is generated from the JDK interface; the dozen methods that
    are actually used are implemented, the rest throw.
  - `java.util.ServiceLoader`: providers come from `META-INF/services` files;
    no module layers. This is what lets the CLDR locale provider start, so
    `Formatter`, `DecimalFormat` and friends run unmodified with English data.
  - `jdk.internal.util.ByteArray(LittleEndian)`: the JDK versions are built on
    byte-array `VarHandle`s.
  - `java.lang.invoke.MethodHandles` and `VarHandle`: only field and array
    element variable handles. Their access modes are signature-polymorphic; the
    interpreter resolves `VarHandle.<mode>` call sites to a synthetic native
    with the call site's descriptor. `java.util.concurrent` (`FutureTask`,
    `AtomicReference`, `CompletableFuture`, …) works unmodified on top.
    Method handles are not supported; nothing in the game uses them.
  - `jdk.internal.vm.SharedThreadContainer`: thread containers without
    `VarHandle`s, used by `ThreadPoolExecutor`.
  - `java.nio` buffers: one class per element type, backed by typed arrays.
    A view of a little-endian aligned `ByteBuffer` (the case libGDX creates
    with `BufferUtils`) aliases the same `ArrayBuffer` as a `Float32Array` etc.,
    so `FloatBuffer.put` is a plain array store and WebGL can take the memory
    directly. Unaligned or big-endian views go through `DataView` natives.
  - `java.util.zip.Inflater/Deflater/CRC32/Adler32` on **pako**'s low-level
    zlib port. Java's `Inflater` is a thin wrapper over zlib, and pako is a
    line-for-line zlib port, so `getRemaining()`, partial flushes and
    dictionaries behave exactly like the JDK (GZIP trailers depend on this).
    pako 1.0.11 was already in the lockfile as a dependency of
    `isomorphic-git`; it is now declared directly. `fflate` is still used for
    jar reading.
  - `java.security.MessageDigest`: MD5, SHA-1 and SHA-256 in JavaScript, no
    provider framework.
- **Runtime contents.** `scripts/javaRunner/buildRuntime.ts` roots the closure
  at the own classes, the VM exceptions, every class the given jars reference,
  and all of `java.lang`, `java.io`, `java.math`, `java.text`, `java.util.**`
  and `java.nio.charset`, plus the English CLDR resource bundles. Packages that
  are VM or OS plumbing are excluded; `java.lang.invoke` classes are included
  only as unlinked leaves so reflection can name them. The generated
  `docs/java-runner/RUNTIME.md` lists what is still missing, every member
  reference that would fail to link, and the borrowed natives.

## 7. Decisions made while building the libGDX bridge (milestones 5 and 6)

- **Backend jar.** The replacement backend lives in
  `components/apps/JavaRunner/java/gdx/com/badlogic/gdx/backends/lwjgl3/` and
  is compiled by `scripts/javaRunner/buildGdx.ts` against the game jar into
  `public/System/JavaRunner/gdx.jar` (Java 11 bytecode). When the app jar
  contains `Lwjgl3Application.class`, the worker puts `gdx.jar` *before* the
  app jar on the class path, so the runner's classes win and the original
  LWJGL backend classes are never loaded. Classes replaced:
  `Lwjgl3Application`, `Lwjgl3Window`, `Lwjgl3Graphics` (with
  `Lwjgl3Monitor`/`Lwjgl3DisplayMode`), `DefaultLwjgl3Input`,
  `Lwjgl3Clipboard`, `Lwjgl3Cursor`, `Lwjgl3Net`, `Lwjgl3NativesLoader`.
  Added: `WebHost` (window/input natives), `WebGL20` and `audio/WebAudio`,
  `WebSound`, `WebMusic`. Kept from the game jar unchanged:
  `Lwjgl3ApplicationConfiguration`, `Lwjgl3WindowConfiguration`, `Lwjgl3Files`,
  `Lwjgl3FileHandle`, `Lwjgl3Preferences`, listeners, the mock audio classes.
  Single window only (`newWindow` throws).
- **WebGL20 is generated.** `buildGdx.ts` writes `WebGL20.java` from the
  `GL20` interface in the jar, every method `native`, so the Java side cannot
  drift from the interface. The JavaScript side (`gdx/gl.ts`) maps GL object
  names to WebGL objects with one handle table, and uniform locations to small
  integers per program.
- **Client-side arrays.** Desktop GL lets `glVertexAttribPointer` and
  `glDrawElements` take a `Buffer`; WebGL does not. Each attribute index gets
  a scratch VBO that receives the buffer's remaining bytes, and client-side
  index draws go through one scratch element buffer, restoring the game's own
  bindings afterwards.
- **Offscreen default framebuffer.** The interpreter yields to the event loop
  whenever a time slice ends, and an `OffscreenCanvas` commits its frame at
  every yield. Drawing straight to the canvas would show half-rendered frames.
  Instead "framebuffer 0" is an internal framebuffer, blitted to the canvas
  right before `WebHost.waitForFrame` waits for the next animation frame.
- **GL version string.** `GLVersion` parses desktop version strings with
  `(\d(\.\d){0,2})`, so `glGetString(GL_VERSION)` answers `2.0 WebGL 2.0 ...`:
  the game sees OpenGL 2.0, which matches the shaders it ships (GLSL 1.00 with
  `#ifdef GL_ES` precision lines).
- **Frame loop.** `Lwjgl3Application` runs the classic loop on the main Java
  thread: poll input, `window.update()` (runnables, input, resize, render),
  app runnables, then `WebHost.waitForFrame()`, a generator native that waits
  on `requestAnimationFrame` (worker) or a zero timeout (Node).
- **Input encoding.** The page sends events as flat integer records
  `[type, a, b, c, d]` already translated to libGDX key codes and logical
  pixel coordinates; `DefaultLwjgl3Input` feeds them through libGDX's own
  `InputEventQueue` and keeps the polling state (`isKeyPressed`,
  `justTouched`, deltas).
- **Saves.** On Linux the game stores data under
  `$XDG_DATA_HOME/.shatteredpixel/shattered-pixel-dungeon/`. The runner sets
  `XDG_DATA_HOME=/Users/Public/Saved Games` for libGDX jars, so saves land in
  `/Users/Public/Saved Games/.shatteredpixel/...` without patching the game.
- **Audio.** `WebAudio.load` copies the file bytes to the page, which decodes
  sounds with `decodeAudioData` and streams music through media elements.
  Sound and music ids are allocated in the worker so `play` can return
  synchronously; completion events come back as messages and fire
  `OnCompletionListener` from `WebAudio.update()` on the render thread.
- **Pixmaps.** `Gdx2DPixmap` pixels are a `Uint8Array` that the Java
  `ByteBuffer` aliases directly, so `Pixmap.getPixels()` and the native
  drawing functions see the same memory. PNG is decoded synchronously by
  `gdx/png.ts`; JPEG (the game's splash art) is decoded by the page through
  `createImageBitmap` when available and is a grey placeholder in Node.
- **FreeType.** Fonts are parsed by `opentype.js` (already a gregOS
  dependency, loaded lazily with `import()`); outlines are flattened and
  rasterized by a signed-area coverage rasterizer in `gdx/freetype.ts`.
  `FT_Stroker` borders are approximated by distance-based dilation of the
  glyph (round joins), which is what the game's `borderStraight=false` asks
  for. Hinting is never applied, matching the game's `Hinting.None`.
- **Native overrides.** `SharedLibraryLoader.load` and
  `GdxNativesLoader.load` become no-ops, the Jamepad natives report no
  controllers, and `TinyFileDialogs` (used only by the game's crash dialog)
  prints its message to standard error instead of loading LWJGL.
- **Instance natives.** Natives for instance methods receive `this` as the
  first argument; the GL table is written without it and wrapped once.
- **`RandomAccessFile` and `FileChannel`.** `FileHandle.map()` (used by
  FreeType) needs both. The runtime now has its own `RandomAccessFile` that
  loads the file into memory and writes it back on close, and a small
  `java.nio.channels` (`FileChannel` with `map`, the channel interfaces).
  Mapped buffers are copies for `READ_ONLY`/`PRIVATE` and alias the file's
  bytes for `READ_WRITE`.

## 8. The JIT (milestone 8)

- **What is compiled.** `jvm/jit.ts` turns a method's bytecode into one
  JavaScript function. Locals and operand stack slots become JavaScript
  variables (`l0…`, `s0…`; the stack depth before every instruction is
  computed by a small dataflow pass), and control flow is a `switch` on the
  current block inside a loop, so straight-line code falls through without
  dispatch. Methods with `jsr`/`ret`, signature-polymorphic calls
  (`MethodHandle.invoke*`, `VarHandle`), or more than 12 KB of bytecode stay
  interpreted.
- **When.** A method is compiled after it has been entered three times by the
  interpreter (`vm.jitThreshold`), or when one of its loops runs long enough to
  hit the interpreter's budget check. Compiled code calls other methods
  directly and compiles them on first call, so hot call graphs move to
  JavaScript together. Virtual and interface calls use a per-site
  monomorphic inline cache on the receiver's class.
- **Suspension instead of blocking.** Compiled code never waits. When it would
  have to (a class that is not initialized yet, a contended monitor, a
  generator native such as file I/O or `Object.wait`, a callee that cannot be
  compiled, a call chain deeper than 700 compiled frames, or the end of the
  thread's time slice at a loop back edge) it throws `Suspend`. Each compiled
  activation on the JavaScript stack catches it, adds an ordinary interpreter
  `Frame` with its locals, stack and resume point, and rethrows. The
  interpreter splices those frames onto the thread and carries on. Because a
  frame can be resumed in compiled code whenever it is on top at a block
  start, long-running loops (such as the libGDX main loop) keep running
  compiled after every suspension; this doubles as on-stack replacement.
- **Re-executing one instruction.** When compiled code hands an instruction to
  the interpreter (class initialization, a contended monitor), the frame
  records `bailPc` so the interpreter executes that instruction itself before
  compiled code takes the frame back.
- **Exceptions.** Java exceptions are JavaScript throws of `JavaThrow`. Each
  compiled function has one `catch` that looks up the handler for the current
  pc, which is kept in `thread.jitPcs[depth]` (set at calls and on every
  throwing path). The same per-depth arrays (`jitMethods`, `jitPcs`) let
  `Throwable` backtraces and `Reflection.getCallerClass` see compiled frames.
- **Correctness check.** The conformance suite runs twice: interpreted and
  with every method compiled on its first call (`jitThreshold = 0`).
- **Result.** Shattered Pixel Dungeon's title scene went from about 37 ms per
  frame (interpreter, before `Frame` preallocation) and 16 ms (interpreter
  after it) to under 4 ms per frame in Node with a mock GL.

## 9. The playthrough script (milestone 7)

`scripts/javaRunner/shattered.cjs` drives the game in headless Chromium the
way a player would: clicks, keys and screenshots only, no hooks into the JVM.
Decisions:

- **Waiting on the game's log, not on time.** The page forwards the worker's
  stdout to the console; the script waits for log lines such as "descend to
  floor 1" or "picked up" before acting, because boot and scene changes take
  very different times under software WebGL.
- **The tutorial gates the floor.** On floor 1 the game hides the entrance
  room's doors until the adventurer's guide has been read
  (`RegularPainter`: "entrance doors on floor 1 are hidden during
  tutorial"). The guide sometimes starts out of sight, so the script walks
  around the room until its red cover shows up, then picks it up and reads
  it. Without this a run can be stuck in a room with no exits, which looks
  like a level generation bug but is not.
- **Zoomed out to explore.** At the default zoom the inventory pane hides
  half of the map. The script zooms out to 1x (16-pixel tiles) so most of
  the floor fits in the free part of the screen.
- **Tiles from colours.** Each 16x16 tile is classified from its pixels:
  unexplored (almost all black), exit stairs (the two greys only the
  stairs-down tile uses), doors (the reddish greys only door frames use in
  the sewer tileset), and floor (not dark, not bright, and not mostly neutral
  grey, which is what walls are). Frontier tiles are floor next to
  unexplored tiles.
- **Remembering tiles across scrolling.** The camera follows the hero, so
  screen positions change every step. The grid offset is estimated from
  where neighbouring pixels change most, summed over every frame because a
  single frame of pixel art often points half a tile off. The scroll between
  two frames is the whole-tile shift that lines up the most explored tiles
  with the fewest explored/unexplored contradictions. With that, each door
  or frontier tile is tried at most twice, so walls at the edge of the map
  and doors already walked through stop attracting the hero.
- **Nearest target first.** Heading for the farthest target made the hero
  walk the same corridors back and forth; nearest-first explores the floor
  room by room.
- **Fights.** Noticed mobs carry a green health bar; a solid horizontal run
  of that green (unlike the log's green text, which is masked out) is
  clicked until the bar disappears, and Q (attack the nearest enemy) is
  pressed after every move.
- **Fallbacks.** When no door or frontier tile is left, the hero travels to
  a random explored floor tile at least eight tiles away (which also scrolls
  hidden parts of the floor out from under the HUD), then to floor near
  unexplored tiles; WASD random walks are the last resort.
- **Staying alive.** After each move, if the health bar is under 60% and no
  enemy is in view, the script rests (Z) until healed. Without this an early
  run died to a sewer snake.
- **Unexpected windows.** Walking onto a chasm asks whether to jump; any
  window with the game's plain dark background in the middle of the screen
  is closed with Escape before the next move.
